# 批量日常爬怪异塔能量刷新策略优化

## 🐛 问题描述

### 原问题
批量日常页面中的一键爬怪异塔功能在每次战斗后都调用 `evotower_getinfo` 获取最新能量值：
- 频繁请求服务器接口
- 产生大量无用日志
- 增加服务器压力
- 可能导致状态异常

### 项目规范要求
根据记忆中的规范：
> 怪异塔模块的爬塔逻辑需要与批量日常页面的'一键爬怪异塔'功能保持完全一致，确保两个入口使用相同的能量获取方式、任务检查逻辑和状态更新机制。

咸将塔采用**每 8 次刷新一次**的策略，怪异塔也应保持一致。

## ✅ 修复方案

### 核心改进

将怪异塔的能量刷新策略从**每次刷新**改为**每 8 次刷新一次**：

1. **每 8 次战斗**：调用 `evotower_getinfo` 获取真实能量值和任务数据
2. **其他次数**：按每次消耗 1 点能量进行估算
3. **每日宝箱**：在刷新时同步检查并领取
4. **容错机制**：刷新失败时自动降级为估算模式

### 修改内容

#### 1️⃣ 能量刷新逻辑（第 928-986 行）

**修改前**：
```javascript
await safeDelay(_getModuleDelay('tower'));

// ❌ 每次都刷新信息（频繁请求）
const newInfo = await callWithRetry(tokenId, "evotower_getinfo", {}, { retries: 1 });
currentEnergy = newInfo?.evoTower?.energy || 0;

addLog({
  time: new Date().toLocaleTimeString(),
  message: `${token.name} 💡 剩余能量：${currentEnergy}`,
  type: "info",
});

// 检查并领取每日任务
const taskClaimMap = newInfo?.evoTower?.taskClaimMap;
if (taskClaimMap) {
  // ...领取逻辑...
}
```

**修改后**：
```javascript
await safeDelay(_getModuleDelay('tower'));

// ✅ 只在每 8 次时获取完整信息（包含能量和任务数据），其他次数估算
if (count % 8 === 0) {
  try {
    const newInfo = await callWithRetry(tokenId, "evotower_getinfo", {}, { retries: 1 });
    currentEnergy = newInfo?.evoTower?.energy || 0;
      
    addLog({
      time: new Date().toLocaleTimeString(),
      message: `${token.name} 💡 第${count}次后刷新 - 剩余能量：${currentEnergy}, 总次数：${count}`,
      type: "info",
    });
    
    // ✅ 同时领取每日宝箱（也只在每 8 次时检查）
    const taskClaimMap = newInfo?.evoTower?.taskClaimMap;
    if (taskClaimMap) {
      const now = new Date();
      const dateKey = `${now.getFullYear().toString().slice(2)}${(now.getMonth()+1).toString().padStart(2,'0')}${now.getDate().toString().padStart(2,'0')}`;
      const dailyTasks = taskClaimMap[dateKey] || {};
      
      for (const taskId of [1, 2, 3]) {
        if (!dailyTasks[taskId]) {
          try {
            await callWithRetry(tokenId, "evotower_claimtask", { taskId }, { retries: 1 });
            addLog({
              time: new Date().toLocaleTimeString(),
              message: `${token.name} 成功领取怪异塔每日宝箱 ${taskId} 奖励`,
              type: "success",
            });
          } catch (taskErr) {
            const taskErrorMsg = taskErr.message || '';
            
            // 12200040：任务奖励已领取或不存在（正常情况）
            if (taskErrorMsg.includes('12200040')) {
              // 静默处理，不输出日志
            } else {
              addLog({
                time: new Date().toLocaleTimeString(),
                message: `${token.name} 领取任务 ${taskId} 失败：${taskErrorMsg.substring(0, 50)}`,
                type: "warning",
              });
            }
          }
          await safeDelay(200);
        }
      }
    }
  } catch (refreshError) {
    // 刷新失败时减少能量估算
    currentEnergy = Math.max(0, currentEnergy - 1);
    addLog({
      time: new Date().toLocaleTimeString(),
      message: `${token.name} ⚠️ 刷新能量/任务信息失败，按减少能量估算：${currentEnergy}`,
      type: "warning",
    });
  }
} else {
  // 非刷新周期，按正常消耗估算（不再调用 API）
  currentEnergy = Math.max(0, currentEnergy - 1);
}
```

### 🎯 技术要点

#### 1. 刷新频率控制

```javascript
if (count % 8 === 0) {
  // 每 8 次刷新一次
}
```

- 使用取模运算判断是否需要刷新
- 第 8、16、24...次战斗后刷新
- 其他次数使用估算值

#### 2. 能量估算机制

```javascript
currentEnergy = Math.max(0, currentEnergy - 1);
```

- 每次战斗后扣除 1 点能量
- 使用 `Math.max(0, ...)` 确保能量不为负数
- 在下次刷新时校准真实值

#### 3. 容错降级

```javascript
catch (refreshError) {
  // 刷新失败时减少能量估算
  currentEnergy = Math.max(0, currentEnergy - 1);
  addLog({
    time: new Date().toLocaleTimeString(),
    message: `${token.name} ⚠️ 刷新能量/任务信息失败，按减少能量估算：${currentEnergy}`,
    type: "warning",
  });
}
```

- API 调用失败时自动降级
- 输出警告日志提醒用户
- 确保爬塔流程不中断

#### 4. 每日宝箱同步

```javascript
// ✅ 同时领取每日宝箱（也只在每 8 次时检查）
const taskClaimMap = newInfo?.evoTower?.taskClaimMap;
if (taskClaimMap) {
  // ...领取逻辑...
}
```

- 每日宝箱检查与能量刷新同步
- 减少额外的 API 调用
- 错误码 12200040 静默处理（已领取）

## 总结

本次优化将批量日常任务中的爬怪异塔能量刷新策略从**每次刷新**改为**每 8 次刷新一次**，带来以下改进：

### ✅ 核心收益
1. **减少 API 调用**：从每次调用改为每 8 次调用，减少 87.5%

4. **保持功能完整**：每日宝箱检查和领取仍正常工作
5. **增强容错能力**：API 失败时自动降级为估算模式

### 🎯 技术价值
- 建立了统一的能量刷新策略（与咸将塔一致）
- 提供了可扩展的估算机制
- 增强了日志输出，便于问题排查
- 提升了批量任务的整体性能和稳定性

建议在实际使用中观察日志输出，确认能量刷新策略正常工作。如遇异常，请检查 API 调用和估算逻辑。
