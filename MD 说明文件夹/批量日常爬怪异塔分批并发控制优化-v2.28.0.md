# 批量日常爬怪异塔分批并发控制优化

## 🐛 问题描述

### 原问题
批量日常页面中的一键爬怪异塔功能使用 `runStreaming` 函数实现**滑动窗口**模式：
- 完成一个账号就立即启动下一个
- 没有明确的批次概念
- 日志不显示批次进度
- 不符合项目规范（应与咸将塔保持一致）

### 项目规范要求
根据记忆中的规范：
> 挂机任务（tasksHangUp.js）的 batchWithRetry 采用**分批并发执行模型**：
> - 每批 maxActive 个账号通过 Promise.all 并发执行
> - 本批全部完成后才执行下一批（非滑动窗口）
> - 日志显示批次进度：📦 批次 N/M 开始执行 X 个账号
> - 重试也采用同样的分批并发模式

## ✅ 修复方案

### 核心改进

将爬怪异塔的执行模式从**滑动窗口**改为**分批并发**：

1. **主执行流程**：每批 maxActive 个账号，全部完成后才执行下一批
2. **重试流程**：同样采用分批并发模式
3. **日志增强**：显示批次进度和账号数量

### 修改内容

#### 1️⃣ 主执行流程（第 1221-1253 行）

**修改前**：
```javascript
await runStreaming(selectedTokens.value, processClimbWeirdTower);
```

**修改后**：
```javascript
// ✅ 分批并发执行：每批 maxActive 个账号，本批全部完成后才执行下一批
const maxActive = batchSettings.maxActive || 5;
const totalTokens = selectedTokens.value.length;
const totalBatches = Math.ceil(totalTokens / maxActive);

addLog({
  time: new Date().toLocaleTimeString(),
  message: `📊 共 ${totalTokens} 个账号，分 ${totalBatches} 批执行，每批 ${maxActive} 个`,
  type: "info",
});

for (let batchIndex = 0; batchIndex < totalBatches; batchIndex++) {
  if (shouldStop.value) break;
  
  const startIdx = batchIndex * maxActive;
  const endIdx = Math.min(startIdx + maxActive, totalTokens);
  const batchTokens = selectedTokens.value.slice(startIdx, endIdx);
  
  addLog({
    time: new Date().toLocaleTimeString(),
    message: `📦 批次 ${batchIndex + 1}/${totalBatches} 开始执行 ${batchTokens.length} 个账号`,
    type: "info",
  });
  
  // 使用 Promise.all 并发执行本批所有账号
  await Promise.all(batchTokens.map(tokenId => processClimbWeirdTower(tokenId)));
  
  addLog({
    time: new Date().toLocaleTimeString(),
    message: `✅ 批次 ${batchIndex + 1}/${totalBatches} 执行完成`,
    type: "success",
  });
}
```

#### 2️⃣ 重试流程（第 1261-1286 行）

**修改前**：
```javascript
for (let retryRound = 0; retryRound < retryCount_max && failedTokenIds.length > 0; retryRound++) {
  if (shouldStop.value) break;
  addLog({ time: new Date().toLocaleTimeString(), message: `等待${retryWaitMs/1000}秒后重试 ${failedTokenIds.length} 个失败账号（第${retryRound+1}/${retryCount_max}轮）`, type: "info" });
  await safeDelay(retryWaitMs);
  const currentRetry = [...failedTokenIds];
  failedTokenIds = [];
  await runStreaming(currentRetry, processClimbWeirdTower);
  currentRetry.forEach(id => { if (tokenStatus.value[id] === "failed") failedTokenIds.push(id); });
}
```

**修改后**：
```javascript
for (let retryRound = 0; retryRound < retryCount_max && failedTokenIds.length > 0; retryRound++) {
  if (shouldStop.value) break;
  addLog({ time: new Date().toLocaleTimeString(), message: `等待${retryWaitMs/1000}秒后重试 ${failedTokenIds.length} 个失败账号（第${retryRound+1}/${retryCount_max}轮）`, type: "info" });
  await safeDelay(retryWaitMs);
  
  // ✅ 重试也采用分批并发模式
  const retryBatches = Math.ceil(failedTokenIds.length / maxActive);
  for (let batchIndex = 0; batchIndex < retryBatches; batchIndex++) {
    if (shouldStop.value) break;
    
    const startIdx = batchIndex * maxActive;
    const endIdx = Math.min(startIdx + maxActive, failedTokenIds.length);
    const retryBatch = failedTokenIds.slice(startIdx, endIdx);
    
    addLog({
      time: new Date().toLocaleTimeString(),
      message: `📦 重试批次 ${batchIndex + 1}/${retryBatches} 开始执行 ${retryBatch.length} 个账号`,
      type: "info",
    });
    
    await Promise.all(retryBatch.map(tokenId => processClimbWeirdTower(tokenId)));
  }
  
  failedTokenIds = selectedTokens.value.filter(id => tokenStatus.value[id] === "failed");
}
```

## 📊 执行模式对比

### 滑动窗口模式（修改前）

```
账号：A B C D E F G H I J (10 个)
maxActive = 3

时间线：
0s  [A B C] 启动
10s A 完成 → [D] 启动 (B C D 执行中)
15s B 完成 → [E] 启动 (C D E 执行中)
20s C 完成 → [F] 启动 (D E F 执行中)
...
```

**特点**：
- ✅ 资源利用率高（始终保持并发）
- ❌ 批次概念模糊
- ❌ 难以追踪整体进度
- ❌ 不符合项目规范

### 分批并发模式（修改后）

```
账号：A B C D E F G H I J (10 个)
maxActive = 3

时间线：
0s   [A B C] 启动 (批次 1/4)
15s  [A B C] 全部完成 → 批次 1 完成 ✅
15s  [D E F] 启动 (批次 2/4)
30s  [D E F] 全部完成 → 批次 2 完成 ✅
30s  [G H I] 启动 (批次 3/4)
45s  [G H I] 全部完成 → 批次 3 完成 ✅
45s  [J]     启动 (批次 4/4)
50s  [J]     完成 → 批次 4 完成 ✅
```

**特点**：
- ✅ 批次清晰，易于追踪
- ✅ 每批完成后有明确反馈
- ✅ 符合项目规范
- ✅ 重试也采用相同模式

## 🎯 技术要点

### 1. 批次计算

```javascript
const totalBatches = Math.ceil(totalTokens / maxActive);
```

- 使用 `Math.ceil` 确保最后一批即使不满也能执行
- 例如：10 个账号，maxActive=3 → 4 批（3+3+3+1）

### 2. 批次切分

```javascript
const startIdx = batchIndex * maxActive;
const endIdx = Math.min(startIdx + maxActive, totalTokens);
const batchTokens = selectedTokens.value.slice(startIdx, endIdx);
```

- 使用 `slice` 切分账号数组
- `Math.min` 确保最后一批不会越界

### 3. 并发执行

```javascript
await Promise.all(batchTokens.map(tokenId => processClimbWeirdTower(tokenId)));
```

- `Promise.all` 并发执行本批所有账号
- 等待所有账号完成才进入下一批
- 任何账号失败不影响其他账号

### 4. 日志增强

```javascript
addLog({
  time: new Date().toLocaleTimeString(),
  message: `📦 批次 ${batchIndex + 1}/${totalBatches} 开始执行 ${batchTokens.length} 个账号`,
  type: "info",
});
```

- 显示当前批次和总批次
- 显示本批账号数量
- 便于用户了解执行进度

## 📈 性能对比

### 场景假设
- 账号数量：100 个
- maxActive：5
- 每个账号执行时间：30 秒

### 滑动窗口模式
- 始终有 5 个账号在执行
- 总耗时：约 100 × 30 / 5 = 600 秒
- 批次概念：无

### 分批并发模式
- 每批 5 个账号，共 20 批
- 每批耗时：30 秒
- 总耗时：20 × 30 = 600 秒
- 批次概念：清晰（20 批）

**结论**：总耗时相同，但分批模式**进度更清晰**，**更符合项目规范**。
