## 1. 项目目标

本项目实现“咸鱼之王”应用宝微信授权后的本地角色资料获取流程：

1. 展示**应用宝授权二维码**；
2. 用户微信扫码、确认授权；
3. 获取并持久化应用宝账号凭据；
4. 通过 MMTLS 获取微信小程序登录 code；
5. 调用 Hortor `comb_login` 获取 `combUser`；
6. 调用游戏 `serverlist` 获取角色与区服列表；
7. 基于选定角色生成并下载 `.bin` 文件。

最终核心产物包括：角色列表、区服 ID、`combUser`、按角色生成的 `.bin` 文件。应用宝账号的长期凭据由 Go 服务持久化，避免每次操作都重新扫码。

## 3. 完整业务链路

```text
应用宝二维码
  ↓ 扫码并确认
Go: POST /qr/{sid}/confirm
  ↓ 保存 openid / token / login_buffer
Go: POST /wxapp/getCode
  ↓ MMTLS 获取小程序 code
Node: POST /api/comb-login
  ↓ Hortor comb_login，获得 combUser
Node: POST /api/serverlist
  ↓ BON + lx 加密请求，获得角色列表
浏览器
  ↓ 选择角色
at.encode(platformData, "lx")
  ↓ 下载 .bin
```

### 3.1 应用宝授权凭据

应用宝授权完成后获得以下数据：

| 字段 | 用途 | 说明 |
|---|---|---|
| `openid` | 账号标识 | 应用宝授权账号标识 |
| `accesstoken` | 短期访问凭据 | 通常约 2 小时 |
| `refreshtoken` | 刷新凭据 | 用于续期，服务端持久化管理 |
| `login_buffer` | MMTLS 登录缓冲 | base64/protobuf 数据，含 ticket 与 device_id |

> 不应将真实 token、code、login_buffer 写入日志、文档、仓库或发送给第三方。

## 5. 应用宝接口与 login_buffer 签名

通过客户端分析与 HttpCanary 抓包，已确认调用：

```text
POST https://yybadaccess.3g.qq.com/pc_yyb_auth/pcyyb_get_wx_login_buffer_auth
```

### 5.1 请求头

```text
content-type: application/json
ual-access-businessid: pc_yyb_auth
ual-access-timestamp: <13 位毫秒时间戳>
ual-access-nonce: <短随机数字>
ual-access-signature: <MD5 签名>
cookie: openid=...; accesstoken=...; refreshtoken=...
user-agent: Mozilla/5.0
```

### 5.2 请求体

```json
{
  "extInfo": {
    "listI": {
      "user_type": {"value": [0]}
    },
    "listS": {
      "access_token": {"value": ["<accesstoken>"]},
      "unionid": {"value": ["<openid>"]},
      "user_id": {"value": ["<openid>"]}
    }
  }
}
```

### 5.3 签名公式

```text
MD5(requestBody + timestamp + "wgrdg373hy26ww2" + nonce)
```

成功响应中的 login_buffer 路径：

```text
ext_info.list_s.login_buffer.value[0]
```

## 6. Hortor comb_login

### 6.1 请求目的

小程序 code 不能直接查询角色，需要调用 Hortor 平台登录接口以获得 `combUser`。

```text
POST https://comb-platform.hortorgames.com/comb-login-server/api/v1/login
```

关键 query 参数：

```text
gameId=xyzwapp
timestamp=<当前毫秒>
version=android-4.2.1-cn-release
cryptVersion=1.1.0
gameTp=app
system=android
deviceUniqueId=<设备 ID>
packageName=com.hortor.games.xyzw
```

### 6.2 请求体加密

`comb_login` 的文本请求体使用原客户端 `de` / `px` 字符串加密链：

```text
JSON
→ UTF-8 base64
→ 固定密钥递归洗牌 6 次
→ 每 3 字符降采样
→ XOR（offset 1）
→ 再次 base64
```

该逻辑由 `index.html` 中 `encryptBody()` 实现；Node 服务只负责转发加密后的文本 body。

成功条件：

```json
{
  "meta": {"errCode": 0, "errMsg": "success"},
  "data": {"combUser": {}}
}
```

`combUser` 必须保留在页面内存中，因为生成 serverlist 请求和 BIN 文件都需要它。

## 7. 角色与区服列表：serverlist

### 7.1 服务端接口

```text
POST https://xxz-xyzw.hortorgames.com/login/serverlist?_seq=3
Content-Type: application/octet-stream
```

由 Node 代理的接口：

```text
POST http://127.0.0.1:4567/api/serverlist
```

### 7.2 请求数据结构

先构造：

```javascript
const platformData = {
  platform: "hortor",
  platformExt: "mix",
  info: combUser,
  serverId: null,
  scene: 0,
  referrerInfo: ""
};
```

再执行：

```javascript
const requestBytes = at.encode(platformData, "lx");
```

其中：

```text
at.encode(data, "lx")
= BON 序列化（Mt.encode）
+ lx 加密（Ud.encrypt）
```

返回二进制经：

```javascript
const response = at.parse(responseBytes);
const roleData = response.getData();
const roles = roleData.roles;
```

解析后的角色按 `power`（战力）降序展示。

## 8. BON、LZ4 与加密模块

### 8.1 文件

```text
D:\WorkSpace\yyb_loging_fenxi\bon-crypto-full.js
```

该文件从 `index-BzcFZcUZ.js` 的连续原始代码块提取，包含且仅包含一组以下定义：

| 标识 | 作用 |
|---|---|
| `Fd` / `Sd` / `Po` | LZ4 实现 |
| `Rd` / `kd` / `Od` | 二进制读写工具 |
| `Td` / `Id` / `Mt` | BON 编码与解码 |
| `Ud` | `lx` 加密方案 |
| `Ld` | `x` 加密方案 |
| `Md` | 自动识别的解密方案 |
| `Nd` / `Pd` | 网络协议对象包装 |
| `at` | 高层 API：`encode`、`parse`、`bon` |

### 8.2 重要约束

曾出现 `Identifier 'Rd' / 'kd' / 'zt' has already been declared` 错误，根因是从多个重叠代码片段合并，导致重复类定义。

正确做法：

1. 只从原始 `index-BzcFZcUZ.js` 的连续片段提取；
2. 范围为 `function Ad(` 到 `bon:Mt}`；
3. 加载前确认 `Rd`、`kd`、`Od`、`Td`、`Id`、`Nd`、`Pd` 各仅出现一次；
4. 页面内不要再重复定义 `Ld` 或其他同名变量。

## 9. BIN 文件生成与下载

### 9.1 BIN 内容

原客户端并非从远端直接下载 BIN，而是基于当前 `combUser` 和选定的 `serverId` 本地生成：

```javascript
const binPlatformData = {
  platform: "hortor",
  platformExt: "mix",
  info: combUser,
  serverId: Number(serverId),
  scene: 0,
  referrerInfo: ""
};

const binData = at.encode(binPlatformData, "lx");
```

结果是 BON 编码并经过 `lx` 加密的二进制内容。

### 9.2 下载方式

浏览器端：

```javascript
const bytes = new Uint8Array(binData);
const blob = new Blob([bytes], {type: "application/octet-stream"});
```

下载文件名格式：

```text
<角色名>_<serverId>.bin
```

### 9.3 前置条件

下载按钮生效需要：

1. 当前页面已通过 `comb_login` 成功得到 `combUser`；
2. `serverlist` 成功得到含 `serverId` 的角色；
3. `bon-crypto-full.js` 加载成功；
4. 不��刷新页面后直接下载。刷新会丢失内存中的 `savedCombUser`，需要重新获取 code 并登录，或后续实现安全的本地保存机制。

### 11.2 常见问题

| 现象 | 原因 | 处理方式 |
|---|---|---|
| `ERR_CONNECTION_REFUSED` | 对应本地服务未启动或端口被占用 | 检查 8080 / 4567 端口与服务进程 |
| 图片被 CSP 拦截 | 预览页面 `img-src` 不允许 8080 地址 | 前端通过 `fetch` 取图片，再转 data URI 显示 |
| `Identifier ... already declared` | bon-crypto 模块有重叠提取内容 | 使用连续原始片段的干净版本，禁止重复内联定义 |
| `/poll` 返回 502 | 新建 QR 会话被后台网络错误影响，或账号流程已走完 | 已通过“使用已保存账号”取得 code 时可忽略该旧会话；必要时刷新二维码 |
| `invalid code` | 使用了错误 appId 对应的 code，或 code 过期/已用 | 必须使用 Go MMTLS 针对目标 app_id 获取的新 code |
| `comb_login` 成功但没有角色 | 未调用 serverlist 或 BON/lx 模块加载失败 | 检查 `Mt` / `at` 是否存在，检查 Node 4567 服务 |
| serverlist 请求失败 | Node 代理未运行或二进制 body 处理错误 | 检查 `/api/serverlist` 与请求 body 的 base64 传递 |

## 12. 安全与维护建议

1. **严禁提交凭据**：openid、access token、refresh token、login_buffer、微信 code、BIN 文件都属于敏感资料。
2. **限制监听地址**：服务应保持 `127.0.0.1`；不要将 Go 或 Node 本地接口暴露到公网。
3. **公网部署必须鉴权**：至少增加 API key、来源限制和 HTTPS。
4. **数据库备份**：Go 服务 SQLite 数据库存储账号与会话；更新服务前先备份 `resource/db/yyb.db`。
5. **BIN 文件分类保存**：建议按账号/区服分目录保存，并避免在公共网盘或聊天群发送。
6. **最小化调试日志**：测试时可记录 status 与错误码；正式使用不要记录完整 token 或请求体。
